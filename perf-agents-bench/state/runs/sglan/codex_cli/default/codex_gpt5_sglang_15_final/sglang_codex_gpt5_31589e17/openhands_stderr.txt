codex
I implemented a padding-aware split for Two-Batch Overlap (TBO) during CUDA Graph replay to avoid wasting compute on padded tokens, and committed the change.

What changed
- File: python/sglang/srt/two_batch_overlap.py:1
  - Added a lightweight module-level override used only during CUDA Graph replay to determine the effective token count for splitting.
  - TboCudaGraphRunnerPlugin.replay_prepare now sets this override using the non-padded token count provided by the runner. It clamps to [0, bs] and only activates for decode mode.
  - compute_split_indices_for_cuda_graph_replay reads this override so the A/B split is computed from real tokens rather than padded slots, reducing overlapped work and memory traffic when padding is present.
  - Kept public API unchanged; logic is a fast path only when padding exists and TBO is enabled.

Performance impact
- When batches are padded during CUDA Graph replay, the TBO split no longer “spends” half the work on padding. This decreases unnecessary attention/MoE work, improves cache efficiency, and reduces communication for the padded region. No functional changes for unpadded or non-TBO paths.

Why this is safe
- The override is set per replay by TboCudaGraphRunnerPlugin.replay_prepare and only applies to decode-mode splits during replay.
- Capture still uses the original split based on the captured size; replay adjusts only the partition point.
- No public API changes; internal behavior remains identical when there’s no padding.
